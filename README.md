# Автоскло — сайт з ремонту сколів лобового скла

Односторінковий сайт: одна продавальна сторінка (головна) плюс службові —
подяка, 404 і політика конфіденційності. Виїзний ремонт — не окрема
сторінка, а блок «Або виїдемо до вас» на головній
(`src/components/Location.astro`), дані для нього — у
`src/content/coverage.yml`. Статична збірка, контент редагує розробник.
Ціль сайту — вхідні дзвінки.

**Ціни на сайті не публікуються** — це рішення замовника, а не забутий
блок. Вартість називає оператор телефоном або у відповідь на фото, тому
в проєкті немає ні блоку цін, ні колекції послуг, ні сум у заголовках
для пошуку. Не повертайте їх «щоб було повніше»: сторінка навмисно
влаштована так, щоб по ціну людина дзвонила.

---

## Швидкий старт

```bash
npm install
npm run dev          # http://localhost:4321
npm run validate     # перевірка контенту без збірки
npm run check:functions  # типи у functions/** (середовище Workers)
npm run build        # продакшн: падає, якщо контент некоректний
```

`npm run check:functions` перевіряє типи в Pages Functions і нічого не
збирає. Конфіг — `tsconfig.functions.json`, окремий від сайту навмисно: у
`functions/**` діє середовище Cloudflare Workers, де `Response`, `fetch` і
`FormData` оголошені інакше, ніж у браузері, і спільний конфіг змушував би
ці оголошення сперечатися. У CI цей крок стоїть **першим** — перевірка
контенту доти падає на заглушках, і все, що після неї, не запускається.

## Типові правки

Шість речей, які доводиться робити найчастіше. Після будь-якої з них —
`npm run build`, далі `git push`; Cloudflare Pages збирає сам. Поки
в проєкті лишаються заглушки з шаблону, продакшн-збірка падає навмисно
і нічого не розгортається — подробиці в «Викласти зміни».

### Поміняти телефон

`src/content/contacts.yml`, поле `phone_main`. Формат строгий:
`+380XXXXXXXXX`, без пробілів і дужок.

Одне значення підставляється одразу в шапку, меню, перший екран, липку
панель дзвінка, контакти, сторінку подяки й розмітку для пошуковиків.
Більше нічого шукати не треба.

Якщо підключений колтрекінг — заповніть `phone_tracking`. Він має
пріоритет при показі, але в розмітці schema.org лишається `phone_main`.

**Про атрибут `data-phone`.** Кожне посилання на телефон його несе
(вісім місць у коді, одинадцять посилань на зібраному сайті). Код сайту
його не читає — це зачіпка для зовнішнього скрипта колтрекінгу, який
підміняє номер уже в браузері. Лишений навмисно: інакше підключення
колтрекінгу означало б правки у восьми компонентах. Не приберіть його
як мертву розмітку.

### Додати пару фото в галерею

1. Покласти знімки в `src/assets/gallery/`
2. Створити файл у `src/content/gallery/` — назва довільна, скажімо
   zirka-01.yml:

```yaml
before: /src/assets/gallery/zirka-01-before.webp
after: /src/assets/gallery/zirka-01-after.webp
damage_type: star      # star | bullseye | combo | crack
size_mm: 12
duration_min: 40
published: true
```

Шлях мусить починатися з `/src/` — саме так, інакше збірка впаде.
Причина: поле описане через `image()`, і шлях на кшталт `/assets/…`
Astro шукає в теці `public/`, де його немає. Валідатор ловить цю
помилку до збірки і пояснює, що виправити.

Галерея зʼявляється на сайті **від чотирьох опублікованих пар**.
Менше — блок прихований.

### Додати відгук

`src/content/reviews/`, новий файл:

```yaml
author: Андрій
text: Текст відгуку, до 400 символів.
rating: 5
date: 2026-09-20
source: Google        # Google | Viber | Особисто
```

Блок зʼявляється **від трьох відгуків**.

**У теці зараз лежать демонстраційні відгуки** (`demo-01.yml` …
`demo-06.yml`) — вигаданий текст, який стоїть, поки немає справжніх.
Вони потрібні, щоб блок було видно локально: інакше при нулі відгуків
він прихований і не видно ні верстки, ні того, як чотири зірки
виглядають поруч із пʼятьма.

**На сайт вони не потрапляють.** `src/lib/site.ts` відкидає відгуки з
`demo: true` у будь-якій збірці — і продакшн, і прев'ю, — тож видно їх
лише в `astro dev`. Валідатор про них попереджає, але збірку не спиняє.
Додаючи справжній відгук, поля `demo` не ставте зовсім — типове
значення `false`. Коли справжніх набереться три, демонстраційні можна
видалити; можна й лишити як зразок формату.

Чому так суворо: від трьох відгуків із них збирається `aggregateRating`
у розмітці для пошуковиків — це зірочки, які Google показує в
результатах. Вигадана оцінка там означає ручну санкцію на весь домен,
тому демонстраційні відгуки виключені з рейтингу ще й окремо
(`src/components/SchemaOrg.astro`) — другим рубежем, якщо фільтр у
`src/lib/site.ts` колись приберуть. А якщо приберуть, помилку про
demo-відгуки треба вернути у валідатор: інакше рубежів не лишиться.

### Додати питання і відповідь

`src/content/faq/`, один файл на питання:

```yaml
question: "Чи можна ремонтувати взимку?"
answer: >-
  Так, але скло має бути сухим і прогрітим.
in_schema: true       # питання піде і в розмітку FAQPage для Google
order: 10             # менше число — вище в списку
```

Порога показу тут немає: блок рендериться з будь-якою кількістю питань.
Розмітка FAQPage є тільки на головній — два FAQPage з тими самими
питаннями Google вважає дублем і може зняти сніпет з обох сторінок.

### Виправити текст на сторінці

Спершу: чи це взагалі текст із розмітки? Частина текстів — контент, і
лежить у YAML:

| Текст на сайті | Файл |
|---|---|
| Питання і відповіді | `src/content/faq/` — один файл на питання |
| Абзац «Умови роботи на місці» | `src/content/coverage.yml`, поле `conditions` |
| Зона виїзду (текст «Або виїдемо до вас» і `areaServed` у schema.org) | `src/content/coverage.yml`, поле `areas` |
| Телефон, Viber, Telegram, адреса, години роботи | `src/content/contacts.yml` |
| Заголовки й описи для пошуку, H1 і підзаголовок першого екрана | `src/content/pages/home.yml` |

| Де на сайті | Файл |

Не знайшли текст у цих трьох таблицях — шукайте в першій, серед
контенту: `grep -rn "шматок тексту" src/` знаходить будь-який рядок
за секунду.

### Викласти зміни

```bash
npm run build      # падає, якщо контент зламано
git add -A && git commit -m "опис змін"
git push
```

**`npm run build` проходить, але контакти на сайті досі несправжні.**
Запобіжник валить збірку лише на заглушках, які він знає в обличчя
(телефон `+380671234567`, `remont_skla`, `Хрещатик 12`,
`ПРІЗВИЩЕ ІМЯ`). Їх замінили 30 вересня 2026 — теж тимчасовими
значеннями, — і перевірка тепер мовчить. Демонстраційні відгуки збірку
більше не спиняють: на сайт вони не йдуть, бо їх відкидає
`src/lib/site.ts`. Що саме лишилось несправжнім — у розділі «Що
замінити перед запуском».

Якщо збірка впала не на заглушках — повідомлення так само називає файл
і пояснює, що саме виправити.

Щоб зібрати попри помилки (наприклад, подивитись локально):
`npm run build:preview`. Саме ним, поки заглушки на місці.

## Що замінити перед запуском

Домен уже підставлений (`avtoskloua.com` в `astro.config.mjs` і
`public/robots.txt`).

> ⚠️ **Контакти в проєкті досі несправжні, і збірка про це вже не
> попереджає.** 30 вересня 2026 заглушки з шаблону замінили на власні
> значення — але теж тимчасові, це підтвердив замовник. Валідатор шукав
> конкретні рядки шаблону (`+380671234567`, `remont_skla`,
> `Хрещатик 12`, `ПРІЗВИЩЕ ІМЯ`), їх більше немає, і перевірка
> проходить мовчки. **Сайт розгортається з цими даними вже зараз** —
> з 12 жовтня 2026, коли демонстраційні відгуки перестали спиняти
> збірку (на сайт вони більше не йдуть). Єдиний запобіжник тепер —
> оця таблиця.

| Файл | Що замінити | Стан |
|---|---|---|
| `src/content/contacts.yml` | `phone_main` — зараз `+380686850086` | тимчасовий |
| `src/content/contacts.yml` | `viber` — зараз `+3806850086` | **помилка**: сім цифр після `+380` замість девʼяти, загубилось `68`. Кнопка Viber веде в нікуди, і збірка цього не ловить — формат `viber` у схемі не перевіряється |
| `src/content/contacts.yml` | `telegram` — зараз `avtoskloua` | збігається з брендом, але не підтверджений |
| `src/content/contacts.yml` | `address` — зараз «Софіївська Борщагівка» | тимчасова |
| `src/content/contacts.yml` | `lat` / `lng` — зараз `50.4472` / `30.5223` | **не оновлені разом з адресою**: це Хрещатик, центр Києва. Їдуть у schema.org, тож Google отримає адресу в Борщагівці й координати в центрі |
| `src/content/contacts.yml` | `hours` — пн–пт 09:00–19:00, сб 10:00–16:00 | не підтверджені. Від них залежить не лише блок контактів, а й обіцянка «передзвонимо зранку» в `src/components/CallbackPromise.astro` |
| `src/pages/polityka-konfidentsiynosti.astro` | `OPERATOR` — зараз «ФОП Фанон Іван Іванович, РНОКПП 0000000000» | тимчасовий; нулі в РНОКПП валідатор не перевіряє |
| `src/content/reviews/demo-*.yml` | демонстраційні відгуки — вигаданий текст | збірку не спиняють і на сайт не йдуть (фільтр у `src/lib/site.ts`); **блок відгуків на сайті порожній**, поки не зʼявляться справжні |

**Чому цей список узагалі потрібен.** Задум був такий, щоб памʼятати не
доводилось: `npm run build` не проходив, поки лишалася бодай одна
заглушка з шаблону, і валідатор називав файл. Задум працює лише проти
рядків, які валідатор знає в обличчя. Коли заглушку замінюють на інше
несправжнє значення, перевірка замовкає — і єдиним запобіжником стає
оця таблиця. Тому її треба правити разом із даними.

Звичайні тексти й фотографії заглушками не вважаються: збірку вони не
спиняють. Відгуки з `demo: true` — окремий випадок: вигаданий відгук на
комерційному сайті вводить покупця в оману, а від трьох відгуків оцінка
ще й їде в розмітку для Google. Раніше збірка спиняла їх нарівні з чужим
телефоном; тепер межу тримає код — на сайт вони не потрапляють, тож і
спиняти через них розгортання нема за що.

Змінні оточення в Cloudflare Pages:

```
PUBLIC_GTM_ID             — Google Tag Manager (звичайна змінна)
OWNER_TG_ID               — особистий Telegram-номер власника
CRM_URL                   — адреса CRM (звичайна змінна, необовʼязкова)
TELEGRAM_BOT_TOKEN        — Secret
TELEGRAM_CHAT_ID          — Secret (група, номер відʼємний)
TELEGRAM_WEBHOOK_SECRET   — Secret
```

`CRM_URL` потрібна лише історії звернень: у боті немає запиту, з якого
можна дізнатися свій домен, тож посилання на картку клієнта він бере
звідси. Не задали — історія приходить без посилання, більше нічого не
міняється.

Привʼязки: `RATE` → KV namespace (обмеження частоти заявок),
`DB` → база D1 (заявки та їхні стани).

## Telegram-бот

Заявки з форми приходять власнику повідомленням у Telegram. Потрібні
дві речі: токен бота і id чату, куди писати.

### 1. Створити бота

У Telegram знайдіть **@BotFather** → `/newbot` → назва → ім'я користувача
(має закінчуватись на `bot`). У відповідь прийде токен виду
`1234567890:AA...`.

### 2. Покласти токен локально

```bash
cp .dev.vars.example .dev.vars
```

Вставте токен у `.dev.vars`. **Цей файл у git не потрапляє** — репозиторій
публічний, а з токеном будь-хто зможе писати від імені бота і читати
заявки клієнтів. Токен нікому не пересилайте: якщо він десь засвітився,
`/revoke` у @BotFather видає новий.

### 3. Дізнатися chat_id

Напишіть своєму боту будь-що в Telegram (спершу `Start`), потім:

```bash
npm run telegram:chat-id
```

Команда покаже знайдені чати. Впишіть потрібний id у `.dev.vars`.
Свій chat_id не видно в інтерфейсі Telegram — його віддає лише API,
тому й знадобився скрипт. Токен він читає з файлу і ніколи не друкує.

**Якщо бот скаржиться на webhook.** Telegram не дозволяє `getUpdates`,
поки в бота зареєстрований webhook — два способи отримувати оновлення
виключають один одного. Це означає, що бот уже десь використовується.
Скрипт покаже адресу того webhook і не чіпатиме його сам. Найчистіший
вихід — завести **окремого бота для сайту**: те, що працює на старому,
лишиться неторканим. Якщо ж той webhook більше не потрібен:

```bash
npm run telegram:chat-id -- --drop-webhook
```

Після цього все, що отримувало оновлення за тією адресою, працювати
перестане — тому прапорець і не вмикається автоматично.

### 4. Перевірити

```bash
npm run telegram:test
```

Має прийти повідомлення. Після цього перезапустіть `wrangler pages dev` —
він підхоплює `.dev.vars` сам, і форма на сайті почне слати справжні
заявки.

### Бот у групі

`chat_id` може вказувати і на групу — тоді заявки бачать кілька людей
(власник, майстри). Це і є цільовий режим: особистий чат був тимчасовим,
поки працює одна людина.

**Порядок переїзду** (робиться один раз, до появи майстрів):

1. **Запишіть теперішнє значення `TELEGRAM_CHAT_ID`** — це особистий
   номер власника. Він знадобиться далі: майбутня CRM заводить першого
   користувача саме по ньому, і плутати його з номером чату не можна.
2. Створіть групу, додайте бота.
3. **Зробіть бота адміністратором із правом видаляти повідомлення.**
   Без цього він не зможе прибрати вашу відповідь із вільною причиною
   відмови — свій запит приберe, а ваш текст лишиться висіти.
4. Напишіть у групі будь-що і запустіть `npm run telegram:chat-id`.
   Скрипт покаже id групи — він відʼємний. Вебхук на час читання
   доведеться зняти (`--drop-webhook`), **потім поверніть його**:
   `npm run telegram:webhook -- <адреса>`.
5. Підставте новий id у `TELEGRAM_CHAT_ID` — локально в `.dev.vars`,
   у продакшні в Cloudflare Pages → Settings → Environment variables.

Старі заявки лишаються привʼязаними до особистого чату: у базі в кожної
збережено свій `chat_id`, тож їхні картки й далі редагуються там, де
надіслані. У групу підуть нові.

**Що міняється в поведінці бота**

Звичайний учасник бачить лише відповіді на власні повідомлення — решту
переписки Telegram йому не віддає. **Адміністратор отримує всі
повідомлення групи**: режим приватності на адміністраторів не діє. Це
ціна за можливість прибирати за собою чат. Обробник `/api/tg` мовчки
виходить на все, що не є відповіддю на його власний запит, тож стороннє
листування нікуди не записується й ні на що не впливає.

**Кнопки зможе натискати будь-хто, кого додали в групу.** Бот заводить
натиснувшого як майстра сам, без підтвердження, — членство в групі і є
межею довіри. Докладно, чому так і як зняти доступ, — у розділі «CRM»,
підрозділ «Майстри й доступи».

Межа ця — саме **група з `TELEGRAM_CHAT_ID`**: в іншому чаті натискач
майстром не стає, діє лише той, кого вже завели. Тому змінна має дві
ролі (адресат картки-замінника й межа довіри), і порожньою лишати її не
можна — без неї межі немає. Забути її непомітно не вийде: без адресата
не доходить і перша картка, тобто бот просто не працює.

Видаляти повідомлення Telegram дозволяє лише протягом 48 годин після
надсилання. Для причини відмови, яку пишуть одразу, це не обмеження.

### У продакшні

Ті самі три змінні (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`,
`TELEGRAM_WEBHOOK_SECRET`) задаються в Cloudflare Pages → Settings →
Environment variables, **усі три типу Secret**. Поряд із ними —
`OWNER_TG_ID`, який секретом не є. `.dev.vars` потрібен тільки для
локального запуску.

### Стан заявки

Заявка приходить двома повідомленнями: знімки (якщо є) і картка з
кнопками. Розділені вони не примхи заради — Telegram не дозволяє
кнопки під альбомом фотографій.

Стани й переходи:

| Стан | Кнопки |
|---|---|
| 🆕 Нова | `В роботу` · `Відмова` |
| 🔧 В роботі | `Виконано` · `Відмова` |
| ✖️ Відмова без причини | чотири причини · `Інша причина` · `Повернути` |
| ✖️ Відмова з причиною, ✅ Виконана | `Повернути` |

Натискання переписує ту саму картку, а не надсилає нову: одна заявка —
одне повідомлення.

**📋 Історія звернень** — окремий рядок під кнопками стану, і лише там,
де в картці вже стоїть попередження «цей номер уже звертався». Умова та
сама, що в попередження: кнопка без попередження обіцяла б те, чого
немає.

Натискання нічого не міняє — ні стану, ні кешбеку, ні картки. Бот
надсилає **відповіддю на картку** окреме повідомлення: дата, значок
стану, номер і сума кожного попереднього звернення з цього номера,
найновіші зверху, плюс «разом сплачено». Поточна заявка в список не
входить — вона над кнопкою. Довгу історію обрізає на десяти останніх
рядком «… ще N раніше»: подробиці все одно дивляться в CRM, і посилання
на картку клієнта стоїть у тому ж повідомленні (якщо задано `CRM_URL`).

Підсумок рахує лише виконані заявки із сумою — те саме правило, що в
картці клієнта: «Повернути» суму не чистить, тож повернена заявка може
тримати стару, і рахувати її означало б завищувати дохід від клієнта.

Повідомлення лишається в переписці: його попросили руками, і прибирати
його за людиною — зайве.

Коли заявку бере людина («В роботу»), у картці зʼявляється рядок
«Майстер: …» — виконавець. Це не те саме, що «хто останній натиснув»
(див. «Майстри й доступи» у розділі «CRM»).

Натиснути двічі не страшно: повтор того самого натиску (людина тапнула
вдруге, Telegram повторив доставку, двоє натиснули одночасно) нічого не
переписує — бот відповідає підказкою «Заявка вже в цьому стані».

#### Причина відмови

«Відмова» переводить заявку у відмову **одразу**, не чекаючи причини:
інакше заявка висіла б у невизначеності щоразу, коли оператора
відвернули. Причину питає вже наступний крок, і вона необовʼязкова — не
натиснули, і нехай.

Готові причини лежать у `REASONS` (`shared/card.ts`). Їх можна
переписувати, але **не переставляти й не видаляти з середини**: у кнопці
їде номер причини, а не текст (64 байти `callback_data` не вміщають
фразу кириличними), тож картка, надіслана старшим кодом, підставила б
причину за старим номером. Додавати — тільки в кінець.

«✍️ Інша причина» надсилає окреме повідомлення з `force_reply`:
оператор пише текст відповіддю, бот вписує його в картку і **видаляє
обидва повідомлення** — і свій запит, і відповідь. У чаті лишається
тільки картка з рядком «Причина: …».

Звʼязок «відповідь → заявка» тримається в KV (той самий простір `RATE`,
ключ `reason:<чат>:<повідомлення>`, година життя). Вгадувати за текстом
не можна: оператор пише в цей чат і сам собі.

«Повернути» очищає причину — повернення означає, що відмова була
помилкою.

**Чому це вимагає перереєстрації вебхука.** Щоб отримати відповідь
оператора, Telegram мусить надсилати не лише натискання, а й звичайні
повідомлення, тож у `allowed_updates` зʼявився `message`. Після
оновлення коду вебхук треба зареєструвати заново:

```bash
npm run telegram:webhook -- https://avtoskloua.com/api/tg
```

Наслідок, про який варто знати: відтепер у `/api/tg` долітає **кожне**
повідомлення з чату. Обробник мовчки виходить на все, що не є відповіддю
на його власний запит, і саме ця властивість тримає бота від реакції на
сторонній текст — її не варто послаблювати.

Усе, що сталося із заявкою, лежить у таблиці `leads` бази D1. Номер у
картці — це `id` рядка. Схема — у теці `migrations/`:
`0001_leads.sql` (таблиця), `0002_notes.sql` (колонка `notes`, у якій
живуть попередження про фото — інакше перший же натиск кнопки стирав би
їх із картки), `0003_decline_reason.sql` (колонка `decline_reason`),
`0004_crm.sql` (поля про виконану роботу й таблиця `users` для CRM),
`0005_source.sql` (звідки прийшла заявка: сайт чи дзвінок),
`0006_assignee.sql` (виконавець заявки — колонки `assignee_id` і
`assignee_name`; наявні рядки переносяться з `actor`),
`0007_assignee_backfill.sql` (виконавець для рядків «в роботі» й
«виконано», яким `0006` його не дала), `0008_cashback.sql` (журнал
кешбеку — таблиця `cashback`; див. «Кешбек» у розділі «CRM») і
`0009_cashback_pct.sql` (ставка, за якою нараховано рядок журналу).

**Перед першим розгортанням треба створити базу й застосувати всі
міграції.** Інакше кожна заявка приходитиме з рядком
«⚠️ Заявку не збережено», і ніхто цього не помітить, поки не почне
рахувати.

```bash
npx wrangler d1 create leads
npx wrangler d1 execute leads --remote --file=migrations/0001_leads.sql
npx wrangler d1 execute leads --remote --file=migrations/0002_notes.sql
npx wrangler d1 execute leads --remote --file=migrations/0003_decline_reason.sql
npx wrangler d1 execute leads --remote --file=migrations/0004_crm.sql
npx wrangler d1 execute leads --remote --file=migrations/0005_source.sql
npx wrangler d1 execute leads --remote --file=migrations/0006_assignee.sql
npx wrangler d1 execute leads --remote --file=migrations/0007_assignee_backfill.sql
npx wrangler d1 execute leads --remote --file=migrations/0008_cashback.sql
npx wrangler d1 execute leads --remote --file=migrations/0009_cashback_pct.sql
```

Імʼя бази — `leads` (`avtoskloua` — це імʼя воркера, не бази; воно стоїть
у `name` конфігу). Файли перелічені по черзі навмисно: у продакшні немає
таблиці відміток, тож застосовувати їх треба руками й у порядку номерів.
Повторний прогін `0002` впаде з `duplicate column name: notes` — це
нешкідливо й означає, що колонка вже на місці.

Далі в Cloudflare Pages → Settings → Functions → D1 bindings додати
привʼязку з іменем `DB` до створеної бази.

**Порядок має значення: спершу міграція, потім код.** Функції читають усі
колонки, які знають, — зокрема `notes`. Якщо розгорнути новий код на базу,
де міграція `0002` ще не застосована, зламаються **всі кнопки** під
картками: запит до бази впаде, і бот перестане відповідати на натискання.
Заявки при цьому продовжать приходити, тож помітно це стане не одразу.
Те саме правило чинне для кожної наступної міграції. Для `0008` ціна
помилки вища — див. «Порядок розгортання» в розділі «Кешбек».

**Локально міграції накочуються інакше** — командою, яка сама пам'ятає,
що вже застосовано (таблиця `d1_migrations` у базі):

```bash
npx wrangler d1 migrations apply DB --local --persist-to .wrangler/state -c wrangler.local.toml
```

Вона бере всі файли з `migrations/` за порядком номерів; прогнати її
двічі безпечно — другого разу вона просто нічого не знайде. Перевірити,
що колонки на місці:

```bash
npx wrangler d1 execute DB --local --persist-to .wrangler/state -c wrangler.local.toml --command "PRAGMA table_info(leads)"
```

**Чому локальні команди різняться від продакшнових.** `wrangler pages dev`
розуміє привʼязку з прапорця (`--d1 DB`), а `wrangler d1 …` — ні, тож
локально їм завжди потрібен `-c wrangler.local.toml`. Команда
`d1 execute <імʼя> --remote` натомість звертається до бази **за іменем**
через API акаунта, і конфігу не потребує — саме тому продакшнові рядки
вище йдуть без `-c`. А от `d1 migrations apply --remote` конфіг вимагає
(«No configuration file found. Create a wrangler.jsonc file to define
your D1 database»), і той конфіг мусив би містити справжній
`database_id`, який суперечить локальному `"DB"` — тому в продакшні
міграції застосовуються файлами, а не цією командою.

У git `wrangler.local.toml` не потрапляє (він у `.gitignore`), тож у
свіжому клоні його треба створити самому. Ось увесь вміст:

```toml
# Тільки для локальних команд wrangler d1 — у git не потрапляє.
#
# Потрібен, бо `wrangler d1 execute` не вміє брати привʼязку з
# прапорця, як це робить `pages dev --d1 DB`. У продакшні привʼязка
# задається в панелі Cloudflare Pages, і цього файлу там немає.
#
# database_id навмисно "DB", а не довільний рядок: саме такий id
# `wrangler pages dev dist --d1 DB` підставляє сам, коли прапорець не
# містить `=<ref>`. Локальне сховище D1 — файл на диску, підписаний
# хешем цього id, тож без збігу `d1 execute` і `pages dev` бачили б
# дві різні порожні бази.
name = "avtoskloua"

[[d1_databases]]
binding = "DB"
database_name = "leads"
database_id = "DB"
```

`database_id` у ньому мусить бути саме `"DB"`, а не довільний рядок:
локальне сховище D1 — файл на диску, підписаний хешем цього id. Якщо
значення розійдеться з тим, що `pages dev --d1 DB` підставляє сам,
`d1 execute` і `pages dev` дивитимуться у дві різні порожні бази —
міграція ляже в одну, а сервер читатиме з іншої. Саме так один прогін
уже дав заявку з номером `0` і рядком «Заявку не збережено» при живій
таблиці.

**Вебхук реєструється один раз** після того, як сайт уже на домені:

```bash
npm run telegram:webhook -- https://avtoskloua.com/api/tg
```

Скрипт спершу покаже, що зареєстровано зараз, і не затре чужий вебхук
мовчки. Зняти: `npm run telegram:webhook -- --delete`.

## CRM

Окремий застосунок для власника: список, картка заявки з діями
(записати на час, закрити із сумою, відмовити, призначити майстра),
картка клієнта з усіма його зверненнями, список «на сьогодні» і
сторінка «Люди» з доступами. Майстри працюють у Telegram, не в CRM
(див. «Майстри й доступи»). Живе в теці
`crm/`, розгортається окремим Cloudflare Worker, а базу ділить із сайтом.

**Заявку можна завести й руками** — вкладка «+ Нова». Це для клієнтів,
які подзвонили, а не заповнили форму: без цього CRM бачила б лише ту
частину потоку, що прийшла з сайту, а на цих даних стоять і історія
клієнта за номером, і майбутні звіти про гроші. Така заявка лягає
«Новою» і без виконавця — щоб її взяв той, хто вільний, або щоб власник
призначив її комусь. Картка йде в групу так само, як у вебзаявки.
Телефон приймається в будь-якому людському вигляді — «067 123 45 67»,
«+380…», «380…» — і зводиться до одного запису, інакше історія за
номером розсипалася б на кількох «різних» клієнтів.

Звідки прийшла заявка, видно в колонці `source` (`site` або `phone`) і
на самій картці.

### Навіщо окремий Worker

Не сторінки сайту й не ще одна Pages Function — з трьох причин:

- **У сайту бюджет швидкості й предохранитель.** Сторінку обмежено
  Lighthouse-порогами, а продакшн-збірка навмисно падає на тимчасових
  даних (див. «Що замінити перед запуском»). CRM — застосунок із
  сесіями й формами, і ні те, ні інше йому не мусить заважати
  розгортатися.
- **У CRM свої залежності й свій деплой.** `hono` та власний
  `package.json` у `crm/` не потрапляють у збірку сайту. Зміна в CRM не
  перезбирає сайт, зміна на сайті не чіпає CRM.
- **Pages не має Cron Triggers.** Нагадування клієнтам і запит відгуку
  після роботи (пізніші куски) запускаються за розкладом, а розклад є
  лише у Workers. Робити CRM окремим Worker із самого початку дешевше,
  ніж переїжджати потім.

### База одна, міграції одні

CRM і сайт читають **ту саму базу D1** (`leads`): заявка, яку створила
форма, одразу видна в списку, а дія в CRM перемальовує картку в групі
Telegram. Тому й **тека міграцій одна — `migrations/` у корені**. У `crm/`
своєї теки немає й бути не повинно.

Дві теки зламали б схему: кожна мала б свою нумерацію й свою таблицю
відміток, і обидві по черзі змінювали б одні й ті самі таблиці. Два файли
`0005_*.sql` з різних тек — це вже конфлікт, якого ніхто не помітить до
першого розгортання. Нову міграцію додавайте в `migrations/` з наступним
номером, хоч би до якого з двох застосунків вона належала.

### Локальний запуск

```bash
cp .dev.vars.example .dev.vars              # якщо ще немає; один файл на сайт і CRM
cp crm/wrangler.local.toml.example crm/wrangler.local.toml
npm --prefix crm install
npm run crm:dev                             # http://localhost:8789
```

Залежності CRM ставляться окремо: `npm install` у корені їх не бачить
(або `cd crm && npm install` — те саме). Порт CRM — **8789**, сайт
поруч працює на 8788, тож обидва можна тримати одночасно.

Три деталі, на яких легко спіткнутися:

- **`database_id` у `crm/wrangler.local.toml` — рівно `"DB"`.** Локальне
  сховище D1 — файл на диску, підписаний хешем цього значення. Якщо
  вписати інше, CRM і сайт дивитимуться у дві різні порожні бази, а
  складається враження, що заявок просто немає. Це вже одного разу
  коштувало проєкту хибного прогону. Файл у git не потрапляє, у
  шаблоні `crm/wrangler.local.toml.example` значення вже правильне.
- **`--persist-to ../.wrangler/state`** у скрипті `dev` спрямовує CRM на
  ту саму локальну базу, що тримає сайт (`.wrangler/state` у корені).
  Без цього CRM створив би власну, порожню, у теці `.wrangler` усередині `crm/`.
- **`--env-file ../.dev.vars`** там само. `wrangler dev -c
  wrangler.local.toml` шукає `.dev.vars` поруч із конфігом, тобто в `crm/`,
  і без цього прапорця воркер не бачить ні токена, ні `SESSION_SECRET`.
  Файл один на двох: сайт і CRM беруть той самий.

Міграції накочуються так само, як для сайту (див. «Telegram-бот»): CRM
стає на ті самі локальні таблиці. Перш ніж запускати CRM, переконайтеся,
що застосовано все до `0009` включно.

Ще одна деталь того самого роду: `npm run crm:seed-owner` (без
`--remote`) ходить у локальну базу через `wrangler d1 execute`, тож
вимагає **кореневого** `wrangler.local.toml` — не того, що в `crm/`.
Його вміст наведено в розділі «Telegram-бот»; без нього скрипт падає з
«No configuration file found».

Типи перевіряє `npm run crm:check`.

### Змінні

Додані два нових; решта спільна з сайтом і береться з того самого
`.dev.vars`:

| Змінна | Що це |
|---|---|
| `SESSION_SECRET` | Ключ, яким підписується кука сесії. Довгий випадковий рядок (`node -e "console.log(crypto.randomUUID()+crypto.randomUUID())"`). Змінити — вигнати всіх із сесій. |
| `OWNER_TG_ID` | **Особистий** Telegram-номер власника — саме людини, а не чату. Потрібен лише скрипту `crm:seed-owner` (див. нижче); читається з оточення або з `.dev.vars`, також для `--remote`. |
| `TELEGRAM_BOT_TOKEN` | Спільний із сайтом: за ним CRM перевіряє підпис входу й перемальовує картки в групі. |
| `TELEGRAM_CHAT_ID` | Спільний із сайтом. Тепер це **відʼємний номер групи**, а не особистий чат — ці два номери не плутайте. |

У продакшні `SESSION_SECRET`, `TELEGRAM_BOT_TOKEN` і (за бажання)
`TELEGRAM_CHAT_ID` задаються секретами самого Worker — `npx wrangler
secret put SESSION_SECRET` із теки `crm/`, — а не в панелі Pages: змінні
сайту CRM не бачить.

### Власник: `npm run crm:seed-owner`

```bash
npm run crm:seed-owner                  # локальна база
npm run crm:seed-owner -- --remote      # продакшн
```

Скрипт читає `OWNER_TG_ID` і заводить власника в таблицю `users` із
роллю `owner`. Без нього **зайти в CRM неможливо**: вхід дає лише рядок
у `users` із роллю `owner`, а такий рядок не заводиться сам — бот
додає майстрів, не власників. Це не
міграція, бо міграція — чистий SQL без змінних оточення, а особистий
номер власника не має лежати у файлі під git. Повторний запуск
безпечний: рядок оновлюється, а не дублюється.

Знятий доступ (`active = 0`) діє негайно: прапорець перевіряється на
кожному запиті, а не лише при вході. Саме це — **єдиний важіль
відкликання доступу**: кнопка «Вийти» лише стирає куку в тому браузері,
де її натиснули, а сама кука лишається дійсною до кінця строку (30
днів), бо сховища сесій немає. Зазвичай доступ знімають на сторінці
«Люди» (див. «Майстри й доступи»). Якщо CRM недоступна, а телефон із
відкритою сесією загубився, — `active = 0` у `users` напряму:

```bash
npx wrangler d1 execute leads --remote --command "UPDATE users SET active = 0 WHERE tg_id = '…'"
```

### Майстри й доступи

**Як зʼявляється майстер.** Нічого вводити не треба: досить додати
людину в групу. Коли вона вперше натисне кнопку під карткою заявки, бот
сам заведе її в `users` з роллю `master` і виконає дію — без
підтверджень і затримки. Власник побачить її на сторінці «Люди» (`/users`)
і в картці заявки: «Майстер: Сергій».

**УВАГА: кого додали в групу, той зможе міняти стани заявок.**
Членство в групі і є межею довіри — окремого дозволу бот не питає.
Для приватної групи власника це рівно те, що потрібно, але людина,
яка додає когось до групи «просто подивитись», мусить знати: ця
людина зможе брати заявки в роботу, закривати їх і відмовляти.
Бухгалтера, партнера чи родича в таку групу додавайте свідомо.

**Дві двері, а не одна.** Кнопки в групі й вхід у CRM — різні речі.
Кнопка міняє стан однієї заявки, яку людина й так бачить у чаті; CRM
показує всю базу: імена, телефони, історію звернень, суми. Тому
автоматичне заведення відчиняє лише перші двері. **У CRM заходить
лише власник** (роль `owner`). Майстер, який спробує зайти, отримає
відмову з поясненням («CRM поки лише для власника. Заявками керуйте
кнопками в групі») і сесії не отримає.

**Як зняти доступ.** Сторінка «Люди» (`/users`): кнопка «Зняти доступ»
біля потрібної людини, «Повернути доступ» — щоб відновити. Діє
негайно й в боті, і в CRM: наступне натискання кнопки в групі отримає
підказку «У вас немає доступу до заявок», а вхід у CRM відхилять.
Чекати нічого не треба — прапорець `active` читається на кожну дію.

**Знятий доступ не повертається сам.** Рядок із `active = 0` бот не
воскрешає, навіть якщо людина лишається в групі й натискає кнопки далі:
інакше «зняти доступ» нічого б не означало. Кнопки під картками для неї
нікуди не зникнуть — Telegram не вміє показувати різні клавіатури різним
учасникам, — але кожне натискання відхиляється, а стан заявки не
міняється. Щоб людина не бачила цих кнопок зовсім, її треба прибрати з
групи. **Видаляти рядок із `users` не можна** — і не тому, що на ньому
тримається історія «хто це робив», хоч і це правда. Рядок із `active =
0` **і є** блокуванням: щойно його видалити, наступне натискання
заведе людину знову, активним майстром. Зняти доступ означає лишити
рядок на місці.

**Чому власнику доступ не знімається.** Якби власник міг зняти доступ
собі, у CRM не зайшов би ніхто: бот заводить майстрів, а власника
заводить лише скрипт `crm:seed-owner`, тобто повертати доступ довелося б
із командного рядка. Тому на сторінці «Люди»
біля власника кнопки немає, а сервер ще й перевіряє роль цілі: вона
читається з бази перед записом, тож запит у обхід кнопки теж
відхиляється зі словами «Власнику доступ не знімається».

**Виконавець і той, хто натиснув.** У заявки два різні поля:

| Поле | Питання | Коли міняється |
|---|---|---|
| `actor_id`, `actor_name` | хто **останній змінив стан** | кожна зміна стану — і кнопкою в групі, і в CRM |
| `assignee_id`, `assignee_name` | **чия це робота** | коли майстер бере заявку або власник її призначає |

| Подія | `actor` | `assignee` |
|---|---|---|
| Майстер натиснув «В роботу» | він | він |
| Власник призначив заявку в CRM | власник | обраний майстер |
| Майстер закрив роботу | він | не міняється |
| «Повернути» в «В роботі» | хто натиснув | не міняється |
| «Повернути» в «Нову» | хто натиснув | **знімається** |

Розділення потрібне, бо власник, перевішуючи заявку, змінює стан сам, а
робити її буде інший. **У картці Telegram рядок «Майстер: …» показує
виконавця**, а не того, хто натиснув останнім; хто саме тиснув, лишається
в базі для розбору. Рядок зʼявляється, коли заявка вже не «Нова» й
виконавець відомий.

Власник призначає майстра в картці заявки в CRM. Призначення «Нової»
заявки переводить її в «В роботі»; з інших станів призначення стану не
чіпає (перевісити можна й виконану). Порожній пункт у списку знімає
виконавця, не змінюючи стану.

Заявка, повернута в «Нову», лишається **нічиєю**: виконавець
знімається — і кнопкою в групі, і в CRM. «Нова» означає «ніхто ще не
взяв», і саме на цьому стоїть призначення. Повернення в «В роботі»
(із «Виконано») виконавця не чіпає — робота лишається тією ж.

**Звіти мусять групувати за `assignee_id`, а не за іменем.**
`assignee_name` — копія імені на момент дії: вона не оновлюється,
якщо людина змінить імʼя в Telegram, і ставить її сама людина. Імʼя —
для показу, ідентифікатор — номер. Групування за іменем розсипало б
одного майстра на кількох або злило б двох тезок. Для цього в базі
є індекс `idx_leads_assignee`.

**Міграція `0006_assignee.sql`** додає ці колонки й переносить у
`assignee` значення `actor` для наявних заявок. Як і кожну міграцію,
її застосовують **до** розгортання нового коду: бот і CRM читають
`assignee_*`, і без колонок обидва впадуть. Команди — у розділах
«Telegram-бот» і «Деплой».

### Вхід: привʼязка домену до бота

Вхід — Telegram Login Widget, паролів немає. Віджет працює **лише для
домену, привʼязаного до бота**, і без цього кроку на сторінці входу
нічого не зʼявиться:

1. У **@BotFather**: `/setdomain` → оберіть бота → введіть домен CRM.
2. Поки бойового домену немає, підходить адреса Worker на
   `*.workers.dev`, яку Cloudflare видає після першого розгортання.
   Коли зʼявиться свій — повторіть `/setdomain` уже для нього.

Імʼя бота для віджета зашите в `crm/src/index.ts` (`BOT_NAME`) — воно не
секрет, але мусить збігатися з ботом, якому привʼязано домен.

Локально віджет не запрацює: потрібен справжній домен, а `localhost`
для нього не годиться. Для розробки сесійну куку підписують тим самим
алгоритмом, що в
`crm/src/auth.ts`, і ходять у CRM із нею.

### Деплой

```bash
npx wrangler d1 create leads        # лише якщо бази ще немає
```

Підставте `database_id` з відповіді в `crm/wrangler.toml` (поки там
заглушка, деплой навмисно впаде — розгорнути CRM у порожнечу гірше, ніж
не розгорнути).

Далі — **міграції, і лише потім код**. Для свіжої бази це всі
файли з `migrations/` по порядку; для наявної — ті, яких там ще немає:

```bash
npx wrangler d1 execute leads --remote --file=migrations/0001_leads.sql
npx wrangler d1 execute leads --remote --file=migrations/0002_notes.sql
npx wrangler d1 execute leads --remote --file=migrations/0003_decline_reason.sql
npx wrangler d1 execute leads --remote --file=migrations/0004_crm.sql
npx wrangler d1 execute leads --remote --file=migrations/0005_source.sql
npx wrangler d1 execute leads --remote --file=migrations/0006_assignee.sql
npx wrangler d1 execute leads --remote --file=migrations/0007_assignee_backfill.sql
npx wrangler d1 execute leads --remote --file=migrations/0008_cashback.sql
npx wrangler d1 execute leads --remote --file=migrations/0009_cashback_pct.sql
```

Чому саме так: CRM читає колонки, яких до `0004` немає
(`appointment_at`, `closed_at`, `amount`, `work_note` і таблицю
`users`), з `0006` — ще й `assignee_id` та `assignee_name`, а з `0008` —
таблицю `cashback`. Колонку `pct` із `0009` не читає жоден список і
жодна картка — її читає лише нарахування, тож без цієї міграції список
і картка клієнта працюють, а кешбек тихо не пишеться: `rateForLead`
падає на «no such column: pct», помилку ловить той самий `try`, що й
решту збоїв синхронізації.

**`0009` накочуйте окремо від зміни відсотка.** Спершу міграцію зі
старим числом у коді, і лише наступним розгортанням — нове число.
Інакше буде хвилина, коли частина рядків лягла зі старою типовою
ставкою, а код уже рахує за новою, і сторож «одна ставка на заявку»
заблокує такі заявки назавжди.

Повторний прогін `0009` падає з «duplicate column name: pct» — як і
`0002`; це означає «вже застосовано», а не поломку. Розгорнути його на базу без них — отримати помилку
бази на першому ж відкритті списку. Без `cashback` помилка тихіша: упаде
картка клієнта, а зміни заявок перестануть нараховувати кешбек (див.
«Кешбек»). Сайт цих колонок не читає, тож для нього порядок не
критичний; для CRM критичний.

Потім сам Worker, секрети й власник — у цьому порядку:

```bash
npm run crm:deploy                      # видає адресу *.workers.dev
cd crm                                  # secret put читає wrangler.toml поруч
npx wrangler secret put SESSION_SECRET
npx wrangler secret put TELEGRAM_BOT_TOKEN
cd ..
npm run crm:seed-owner -- --remote
```

> ⚠️ **Тип значення — саме Secret, не Text.** У панелі Cloudflare
> випадний список типово стоїть на Text, а `wrangler deploy` бере
> перелік звичайних змінних із конфіга — і стирає ті, яких там немає.
> Секрети він не чіпає ніколи. 12 жовтня 2026 на цьому вже спіткнулися:
> `TELEGRAM_BOT_TOKEN` і `SESSION_SECRET`, додані як Text, зникли на
> першому ж розгортанні, і CRM стала відповідати 503. Перевірити, що
> на місці, можна так:
>
> ```bash
> cd crm && npx wrangler secret list
> ```

Секрети ставляться **після** першого розгортання не з недогляду:
`wrangler secret put` вимагає, щоб Worker уже існував. Проміжок при
цьому безпечний — поки `SESSION_SECRET` або `TELEGRAM_BOT_TOKEN`
порожній, CRM відповідає **503** і сторінкою «не налаштовано» на кожен
запит, крім `/health`. Інакше було б гірше за незручність: без
справжнього токена перевірка підпису Telegram відкривалася б публічно
відомим ключем (SHA-256 від порожнього входу), і зайти міг би будь-хто,
хто знає адресу. `crm:seed-owner` — останнім: доступ дає саме пара
«секрети на місці» плюс «рядок у `users` із роллю `owner`».

### Ранкове зведення

О восьмій ранку в групу приходить повідомлення: хто записаний на
сьогодні, і скільки заявок ніхто не взяв довше доби. Якщо сказати нема
чого — ні записів, ні залежаних, — повідомлення не надсилається
взагалі. Щоденне «записів немає» привчило б не читати його зовсім.

Робить це cron на воркері CRM (`[triggers]` у `crm/wrangler.toml`),
а не Pages: у Pages Functions cron-тригерів немає взагалі, і це одна з
причин, чому CRM окремим воркером.

**Чому два запуски, 05:00 і 06:00 UTC.** Київський час випереджає UTC
на дві години взимку і на три влітку, тож одна фіксована година UTC
двічі на рік уїжджала б. Працює той запуск, що припав на 8 ранку в
Києві, — годину перевіряє сам обробник (`scheduled()` у
`crm/src/index.ts`). Перевірено на обидва боки переходу: жодного дня з
двома повідомленнями чи без жодного.

Текст збирає `digestText()` у `crm/src/digest.ts` — чиста функція без
бази й мережі. Щоб побачити всі випадки, її досить викликати з
вигаданими рядками; надсилати щось у Telegram для цього не треба.

Кнопок у зведенні немає навмисно: стан заявки міняється в її власній
картці. Друге місце, де можна натиснути, рано чи пізно розійшлося б із
першим.

### Кешбек

Клієнтові нараховується **10% від суми закритої заявки**. Нарахування
лягає на номер телефона — той самий ключ, за яким зібрана картка
клієнта, — тож усі звернення з одного номера копичать на один баланс
(таксопарк із одним номером і двадцятьма авто — це один баланс, родина
з двома телефонами — два). Зараз кешбек лише **накопичується**: списання
не існує ні в базі, ні в інтерфейсі, ні в боті.

**Коли нараховується.** Не по кнопці, а за станом заявки: у момент, коли
в неї є і стан «Виконана», і сума. Бот може закрити заявку без суми, а
CRM вписати її потім, — подій, після яких треба перерахувати, кілька, і
ловити кожну окремо означало б колись одну пропустити. Тому після
кожної дії, що проходить через CRM (`/appoint`, `/unappoint`, `/close`,
`/decline`, `/undo`), і після кожного успішного переходу стану в боті
(«В роботу», «Виконано», «Відмова», «Повернути») викликається одна
операція `syncCashback` (`shared/cashback.ts`). У боті вона стоїть
одразу після успішного `UPDATE` переходу; кнопки готової причини відмови
і відхилені натискання («заявка вже в цьому стані», «спершу Повернути»)
повертаються раніше й її не викликають. Призначення виконавця
(`/lead/:id/assign`) і створення заявки вручну її не викликають свідомо:
`assign` стан таки міняє, але лише `new → in_work`, а заявці без закриття
кешбек не належить, тож журнал до й після цього переходу однаковий;
нова заявка стоїть у `new`, їй нема за що нараховувати, а суму жодна з
двох дій не чіпає. Операція рахує, скільки заявці належить зараз
(10% від `amount`, якщо `status = 'done'` і сума є; інакше нуль), і
дописує різницю з тим, що вже записано за цією заявкою. З цього
випливає все потрібне без окремих гілок:

- закрили із сумою 1 200 ₴ — у журналі +120 ₴;
- виправили суму на 900 ₴ — належить 90, записано 120, дописується −30;
- повернули в роботу — належить 0, дописується −90;
- закрили кнопкою в боті без суми — належить 0, нічого не пишеться;
- та сама подія прилетіла двічі — різниці нема, рядка нема (бот
  отримує повторні доставки того самого натискання, і це нешкідливо).

Повторне закриття зі старою сумою — не виняток, а той самий випадок.
«Повернути» суму не чистить навмисно (див. `crm/src/db.ts`), тож заявка,
закрита вдруге кнопкою в боті без суми, знову належить за стару суму, і
журнал дописує нарахування. Це та сама робота за ту саму суму; баланс
виходить такий, ніби повернення не було.

**Копійки й округлення.** Суми в базі — цілі копійки (`leads.amount`,
`cashback.kop`). 10% рахується з округленням **вниз**: з 1 200,50 ₴
(120050 коп) виходить 120,05 ₴ (12005 коп), а з 99,99 ₴ — 9,99 ₴.
Пообіцяти менше й віддати більше краще, ніж навпаки. Відсоток — константа
`CASHBACK_PCT` у `shared/cashback.ts`, а не змінна оточення: зміна
відсотка має лишати слід у git.

**Де видно.** У картці клієнта в CRM — баланс і журнал, з якого він
склався. У картці заявки в Telegram — один рядок «Кешбек: …», лише коли
баланс більший за нуль; це баланс людини за номером, а не нарахування
за цю заявку. Рахується в момент малювання картки (`functions/api/lead.ts`
і `shared/notify.ts`).

**Чого немає свідомо.** Списання, потолка й мінімальної суми; строку дії
й згорання; передачі іншій людині; повідомлення клієнтові (ні SMS, ні
месенджера — баланс називає майстер у розмові); донарахування за заявки,
закриті до появи цієї можливості (на момент запуску в базі не було жодної
закритої); окремого відсотка для заміни скла. Що лишається вирішити
власнику майстерні — у `docs/superpowers/specs/2026-10-21-cashback-design.md`.

#### Журнал ніколи не редагується

Нарахування живуть у таблиці `cashback` (міграція `0008_cashback.sql`),
один рядок — одна подія: номер, заявка, `kop`, час. Поля «баланс» нема
ніде: баланс — це `SUM(kop)` за номером. Відкат нарахування — не
видалення, а **ще один рядок із мінусом** (у CRM він підписаний
«сторно»; так бухгалтери називають запис, що скасовує попередній).

**Не робіть `UPDATE` і `DELETE` над `cashback`.** Людині вже назвали
суму, і історія, з якої вона складена, мусить лишитися; виправлене
число заднім числом не відрізнити від того, що колись пообіцяли.
Виправлення — завжди новий рядок (приклад — нижче).

#### Порядок розгортання

Міграцію `0008` накочують **до** коду — як і кожну міграцію (команди в
розділі «Деплой»). Тут ціна помилки вища за звичайну, і вона підступна,
бо нічого не падає на очах. Якщо код CRM або функцій піде раніше, ніж
з'явиться таблиця `cashback`:

- зміни заявок (`/appoint`, `/unappoint`, `/close`, `/decline`, `/undo`
  і переходи стану кнопками бота в групі) **проходять**, але нарахування
  не записується: збій синхронізації навмисно не валить зміну, а лише
  пишеться в журнал (див. «Звірка журналу із заявками»);
- картка клієнта в CRM, яка читає журнал, відповідає **500**;
- заявки, закриті в цей проміжок, лишаються без кешбеку, доки їх не
  знайдуть запитом звірки й не допишуть рядок — самі вони не виправляться,
  поки з заявкою не станеться нова дія з наведеного вище переліку.

Тому порядок такий: міграція, перевірка, що таблиця є, потім код.
Перевірка — відповідь має містити один рядок `cashback`, порожня
відповідь означає, що міграцію не накочено:

```bash
npx wrangler d1 execute leads --remote --command "SELECT name FROM sqlite_master WHERE name='cashback'"
```

#### Звірка журналу із заявками

Збій синхронізації не валить зміну заявки, а пишеться в журнал одним
рядком: «журнал кешбеку не синхронізовано (заявка #N)». З префіксом
`applyChange:` його пише воркер CRM (`avtoskloua-crm`), з префіксом `tg:` —
Pages Function бота (`functions/api/tg.ts`, проєкт Pages `avtoskloua`).
Видимість у цих двох боків різна:

- воркер CRM має `[observability] enabled = true` (`crm/wrangler.toml`),
  тож його журнал зберігається: рядок `applyChange:` можна знайти в панелі
  Cloudflare заднім числом;
- у Pages Functions такого конфігу немає взагалі, тож рядок `tg:` видно
  лише живим потоком (`wrangler pages deployment tail`): якщо в той момент
  ніхто не дивився, коли гроші не зійдуться, його вже не існує.

Тому відсутність рядка `tg:` нічого не доводить, а надійний слід
розбіжності — запит звірки нижче.

Коли таблиці `cashback` нема, з обох боків сиплеться ще й третій рядок:
`drawCard: баланс кешбеку для заявки #N не прочитано` (`shared/notify.ts`).
Його пише перемальовування картки в Telegram, яке запускають і воркер CRM,
і Pages Function: картка при цьому все одно малюється, лише без рядка
кешбеку. Видимість така сама, як у решти: якщо його написав воркер CRM,
він лишається в журналі; якщо Pages Function — він є лише в живому потоці.

Журнал кешбеку після такого збою лишається хибним, доки з заявкою не станеться
нова дія. Тому є запит, який показує розбіжності прямо в базі. Для
кожної заявки він порівнює суму рядків журналу з тим, скільки їй
належить зараз, і виводить лише ті, де не сходиться; порожня відповідь —
усе гаразд. Запит нічого не змінює.

```sql
-- Звірка журналу кешбеку із заявками. Нічого не змінює.
-- Ставку бере з першого рядка журналу заявки — тієї, за якою їй
-- нарахували. Число 10 стосується лише заявок, яким ще не нараховували:
-- це поточний CASHBACK_PCT з shared/cashback.ts, міняти разом.
WITH logged AS (
  SELECT lead_id, SUM(kop) AS kop, MIN(phone) AS phone
    FROM cashback
   GROUP BY lead_id
),
ids AS (
  SELECT id AS lead_id FROM leads
  UNION
  SELECT lead_id FROM logged
),
calc AS (
  SELECT i.lead_id,
         COALESCE(l.phone, g.phone) AS phone,
         l.status,
         l.amount,
         CASE WHEN l.status = 'done' AND l.amount IS NOT NULL
              THEN l.amount * COALESCE(
                     (SELECT pct FROM cashback c2
                       WHERE c2.lead_id = i.lead_id ORDER BY c2.id LIMIT 1), 10
                   ) / 100
              ELSE 0 END AS owed_kop,
         COALESCE(g.kop, 0) AS logged_kop
    FROM ids i
    LEFT JOIN leads  l ON l.id = i.lead_id
    LEFT JOIN logged g ON g.lead_id = i.lead_id
)
SELECT lead_id, phone, status, amount, owed_kop, logged_kop,
       owed_kop - logged_kop AS diff_kop
  FROM calc
 WHERE owed_kop <> logged_kop
 ORDER BY lead_id;
```

**Змінити відсоток безпечно.** Ставка, за якою нарахували, лежить у
самому рядку журналу (колонка `pct`), і `rateForLead` бере її з першого
рядка заявки. Тому після зміни `CASHBACK_PCT` з 10 на 15 стара закрита
заявка рахується за десятьма й далі — і при уточненні суми, і після
повернення, і при повторному закритті. Доплати за роботу, зроблену за
старими правилами, не буде: нова ставка діє лише на заявки, за які ще не
нараховували.

Межа проходить по **першому нарахуванню**, тобто по тому моменту, коли
в заявки вперше є і стан «виконана», і сума. Не по тому, коли клієнт
звернувся: заявка, що прийшла до зміни, а закрита після, рахується за
новою ставкою.

Звідси одне практичне правило. Бот закриває заявку кнопкою **без суми**,
а суму вписують у CRM пізніше — і ставку фіксує саме той, пізніший
момент. Тож **міняйте відсоток у день, коли немає виконаних заявок без
суми**: інакше робота, зроблена за старою ставкою, але оцінена вже
після зміни, порахується за новою. Знайти такі заявки:

```sql
SELECT id, created_at, closed_at FROM leads
 WHERE status = 'done' AND amount IS NULL ORDER BY id;
```

Число `10` у запиті звірки — запасне, для заявок, яким ще не
нараховували; міняти його треба разом із константою, інакше запит
покаже для таких заявок не ту очікувану суму. На вже нарахованих воно
ні на що не впливає.

**Яка команда для якої бази.** Для локальної — `--file`: коментарі в
запиті кириличні, а в `--command` кирилиця псується (див. «Пастка:
кирилиця у `--command`»). Збережіть запит у файл (UTF-8) і запустіть:

```bash
npx wrangler d1 execute DB --local --persist-to .wrangler/state -c wrangler.local.toml --file=reconcile.sql
```

Для **продакшну `--file` не годиться**: `--remote --file` іде через
імпорт у D1 і друкує лише лічильники («Rows written: 0» та подібне), а
рядків запиту не показує — здаватиметься, що розбіжностей нема. Тут
потрібен `--command` з однорядковою версією без коментарів (кирилиці в ній
нема, тож пастка з розділу нижче не діє). Це той самий запит, зібраний в
один рядок:

```bash
npx wrangler d1 execute leads --remote --command "WITH logged AS ( SELECT lead_id, SUM(kop) AS kop, MIN(phone) AS phone FROM cashback GROUP BY lead_id ), ids AS ( SELECT id AS lead_id FROM leads UNION SELECT lead_id FROM logged ), calc AS ( SELECT i.lead_id, COALESCE(l.phone, g.phone) AS phone, l.status, l.amount, CASE WHEN l.status = 'done' AND l.amount IS NOT NULL THEN l.amount * COALESCE( (SELECT pct FROM cashback c2 WHERE c2.lead_id = i.lead_id ORDER BY c2.id LIMIT 1), 10 ) / 100 ELSE 0 END AS owed_kop, COALESCE(g.kop, 0) AS logged_kop FROM ids i LEFT JOIN leads l ON l.id = i.lead_id LEFT JOIN logged g ON g.lead_id = i.lead_id ) SELECT lead_id, phone, status, amount, owed_kop, logged_kop, owed_kop - logged_kop AS diff_kop FROM calc WHERE owed_kop <> logged_kop ORDER BY lead_id;"
```

Колонки: `owed_kop` — що заявці належить зараз, `logged_kop` — що записано
в журналі, `diff_kop` — різниця, яку дописала б синхронізація (усе в
копійках). Ціле ділення на 100 відкидає залишок, тож
збігається з округленням вниз у коді (суми невідʼємні). Заявка, якої вже
нема в `leads`, а рядки в журналі є, теж потрапляє у відповідь, з порожніми
`status` і `amount`: належить їй нуль.

**Межі звірки.** Вона йде за номером заявки (`lead_id`), а не за
телефоном: якщо телефон у журналі розійдеться з телефоном заявки, запит
цього не покаже.

**Тестові заявки.** Заявка з іменем на «ТЕСТ», закрита із сумою, нарахує
справжній кешбек на той номер, який у ній стоїть. Видалення такої заявки
(рецепт — у розділі «Пастка…» нижче) лишає рядок у журналі без заявки:
звірка його ловить, а виправляється він рядком із мінусом, як нижче.

**Як виправити розбіжність — новим рядком, а не правкою.** Візьміть
`phone`, `lead_id` і `diff_kop` з відповіді й допишіть рівно цю різницю.
**Ставку обовʼязково вкажіть ту саму, що в заявки**, інакше рядок піде з
типовою 10 і зіпсує дві речі одразу: звірка знову покаже розбіжність, а
сторож «одна ставка на заявку» заблокує всі подальші нарахування цієї
заявки. Підзапит бере ставку сам — із першого рядка заявки, а для
заявки без рядків із поточної константи:

```sql
INSERT INTO cashback (phone, lead_id, kop, created_at, pct)
VALUES ('<phone>', <lead_id>, <diff_kop>, strftime('%Y-%m-%dT%H:%M:%fZ', 'now'),
        COALESCE((SELECT pct FROM cashback WHERE lead_id = <lead_id> ORDER BY id LIMIT 1), 10));
```

Число 10 у підзапиті — поточний `CASHBACK_PCT`; якщо константу змінили,
підставте нове число.

Після цього запит звірки на цю заявку мовчить. Нова дія над заявкою з
переліку вище (`/unappoint`, `/close`, `/undo`, кнопка бота) теж
вирівняє журнал сама, але призначення виконавця — ні: воно синхронізації
не викликає.

### Пастка: кирилиця у `--command`

Кирилиця в `--command` для `wrangler d1 execute` **псується в Git Bash**:
запит доходить до бази зіпсованим і **мовчки не зачіпає жодного
рядка** — ні помилки, ні попередження. Тому будь-який запит із
кириличним текстом (наприклад, `DELETE FROM leads WHERE name LIKE
'ТЕСТ%'`) пишіть у файл (UTF-8) і запускайте через `--file`:

```bash
npx wrangler d1 execute DB --local --persist-to .wrangler/state -c wrangler.local.toml --file=query.sql
```

Схожа пастка з HTTP-запитами: `curl.exe` на Windows надсилає тіло в
CP1251, а не в UTF-8. Для тіла з кирилицею беріть Node з `fetch` і
`FormData`.

## Архітектура

```
Контент (YAML) ──> validate-content.mjs ──> Astro build ──> Cloudflare Pages
```

**Ключовий принцип:** зламати продакшн неможливо. Помилка в контенті зупиняє
збірку, живий сайт лишається в останньому робочому стані.

### Валідація контенту

Два інструменти з різними ролями:

- `src/content.config.ts` і `src/lib/site.ts` — zod-схеми: типи,
  обовʼязковість полів, межі значень. Падають під час збірки.
- `scripts/validate-content.mjs` — те, чого схеми не вміють:
  заглушки з шаблону, існування фотографій галереї на диску та їхній
  розмір по короткій стороні, пороги показу блоків.

### Запобіжник для самої документації

Той самий скрипт перевіряє і README: кожен шлях, узятий тут у зворотні
лапки, мусить існувати на диску. Немає — попередження з назвою шляху.
Помилкою це не робиться навмисно: застарілий рецепт не причина не
випускати сайт.

Перевіряються лише схожі на шлях рядки — з розширенням або зі скісною
рискою. Команди (`npm run build`), значення (`+380XXXXXXXXX`), адреси
і глоби з `*` не чіпаються. Рядок «перевірено шляхів із README» у
статистиці показує, скільки їх узято до уваги.

Причина проста: рецепти вище називають конкретні файли, і рецепт,
що вказує на перенесений файл, шкодить більше, ніж його відсутність.
Чого перевірка не ловить — це посилання на **не той** наявний файл;
тут допоможе тільки уважність.

Раніше вони навмисно дублювали одне одного, бо контент редагував власник
через CMS і йому потрібні були пояснення українською. CMS більше немає,
дублювання прибрано.

Окремо валідатор ловить дві речі, які не є «контентом», але ламають запуск:
заглушки з шаблону (див. вище) і неправильні шляхи до фото галереї — коли
шлях не починається з `/src/`.

**Про шлях до фото варто знати окремо.** Він має починатися з `/src/`:
поле описане через `image()`, і шлях на кшталт `/assets/…` Astro шукає
в теці `public/`, де файлу немає. Валідатор ловить цю помилку до збірки.

### Умовні блоки

Порогові значення в `src/lib/site.ts`:

- галерея рендериться від **4 опублікованих пар**
- відгуки — від **3 штук**

Менше — блок не з'являється. Порожні рамки гірші за відсутній блок.

## Бюджет продуктивності

Перевіряється в CI (`lighthouserc.json`), збірка падає при порушенні:

| Метрика | Ліміт |
|---|---|
| Performance | ≥ 0.95 |
| Accessibility | ≥ 0.95 |
| SEO | 1.0 |
| LCP | ≤ 2000 мс |
| CLS | ≤ 0.02 |
| `uses-responsive-images` | без зауважень (жодного зображення, більшого за потрібний розмір) |

Ще два бюджети — на рівні попередження, збірку не спиняють: вага сторінки
до 500 КБ і невикористаний JS до 10 КБ.

Емуляція: середній Android, 4× уповільнення CPU, три прогони.

**Чого не робити:** не додавати зовнішні шрифти, не вбудовувати Google Maps
iframe, не ставити React заради одного компонента. Кожне з цього самотужки
з'їдає бюджет.

### Про шрифт

Заборона на зовнішні шрифти лишається в силі — вона про запит на чужий домен
перед першим рендером. Шрифт сайту (Onest, SIL OFL) інший випадок: один
варіативний woff2 на 34 КБ із вирізаною кирилицею й латиницею, на нашому ж
домені, з `preload` і кешем на рік. Файл — `public/fonts/onest-var.woff2`,
ліцензія поруч.

Ціна виміряна, а не припущена: LCP 916 → 1371 мс при ліміті 2000. Системний
шрифт був головною причиною, чому сайт читався як шаблон, і півсекунди
запасу за це — прийнятний обмін. Якщо колись знадобиться повернути LCP,
найдешевший крок — `font-display: optional` замість `swap`: перший візит
побачить системний шрифт, повторні — свій.

Ім'я файлу не містить хеша, а кешується на рік. Оновлюєте шрифт — давайте
файлу нове ім'я.

## Аналітика

Один делегований слухач у `src/components/Analytics.astro` ловить усі
конверсійні кліки. Події: `click_phone`, `click_viber`, `click_telegram`,
`form_submit`, `form_step`, `scroll_75`.

`form_step` шле скрипт форми заявки (`src/components/LeadForm.astro`) при
кожному переході між кроками майстра — несе номер кроку (`step`), на який
перейшли. Без неї неможливо дізнатися, на якому екрані майстра люди йдуть.

Атрибут `data-cta` на посиланні дає розбивку за місцем: `header`, `menu`,
`hero`, `sticky`, `contacts`. Значення `form_home`, яке форма заявки
ставить через проп `placement`, сюди не належить: слухач читає `data-cta`
лише з `a[href]` (`tel:`/`viber:`/`t.me`), а кнопка відправки форми —
не посилання, тож це значення в аналітику не потрапляє.

GTM вантажиться через 1,2 с після `load` — аналітика не впливає на LCP.
