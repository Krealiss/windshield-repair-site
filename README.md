# Автоскло — сайт з ремонту сколів лобового скла

Односторінковий сайт: одна продавальна сторінка (головна) плюс службові —
подяка, 404 і політика конфіденційності. Виїзний ремонт — не окрема
сторінка, а блок «Або виїдемо до вас» на головній
(`src/components/Location.astro`), дані для нього — у
`src/content/coverage.yml`. Статична збірка, контент редагує розробник.
Ціль сайту — вхідні дзвінки.

**Ціни на сайті не публікуються** — це рішення замовника, а не забутий
блок. Вартість називає оператор телефоном або у відповідь на фото, тому
в проєкті немає ні блоку цін, ні колекції послуг, ні сум у заголовках
для пошуку. Не повертайте їх «щоб було повніше»: сторінка навмисно
влаштована так, щоб по ціну людина дзвонила.

```bash

npm run validate     # перевірка контенту без збірки

```

## Типові правки

Шість речей, які доводиться робити найчастіше. Після будь-якої з них —
`npm run build`, далі `git push`; Cloudflare Pages збирає сам. Поки
в проєкті лишаються заглушки з шаблону, продакшн-збірка падає навмисно
і нічого не розгортається — подробиці в «Викласти зміни».

### Поміняти телефон

`src/content/contacts.yml`, поле `phone_main`. Формат строгий:
`+380XXXXXXXXX`, без пробілів і дужок.

Одне значення підставляється одразу в шапку, меню, перший екран, липку
панель дзвінка, контакти, сторінку подяки й розмітку для пошуковиків.
Більше нічого шукати не треба.

Якщо підключений колтрекінг — заповніть `phone_tracking`. Він має
пріоритет при показі, але в розмітці schema.org лишається `phone_main`.

**Про атрибут `data-phone`.** Кожне посилання на телефон його несе
(вісім місць у коді, одинадцять посилань на зібраному сайті). Код сайту
його не читає — це зачіпка для зовнішнього скрипта колтрекінгу, який
підміняє номер уже в браузері. Лишений навмисно: інакше підключення
колтрекінгу означало б правки у восьми компонентах. Не приберіть його
як мертву розмітку.

### Додати пару фото в галерею

1. Покласти знімки в `src/assets/gallery/`
2. Створити файл у `src/content/gallery/` — назва довільна, скажімо
   zirka-01.yml:

```yaml
before: /src/assets/gallery/zirka-01-before.webp
after: /src/assets/gallery/zirka-01-after.webp
damage_type: star      # star | bullseye | combo | crack
size_mm: 12
duration_min: 40
published: true
```

Шлях мусить починатися з `/src/` — саме так, інакше збірка впаде.
Причина: поле описане через `image()`, і шлях на кшталт `/assets/…`
Astro шукає в теці `public/`, де його немає. Валідатор ловить цю
помилку до збірки і пояснює, що виправити.

Галерея зʼявляється на сайті **від чотирьох опублікованих пар**.
Менше — блок прихований.

### Додати відгук

`src/content/reviews/`, новий файл:

```yaml
author: Андрій
text: Текст відгуку, до 400 символів.
rating: 5
date: 2026-09-20
source: Google        # Google | Viber | Особисто
```

Блок зʼявляється **від трьох відгуків**.

### Додати питання і відповідь

`src/content/faq/`, один файл на питання:

```yaml
question: "Чи можна ремонтувати взимку?"
answer: >-
  Так, але скло має бути сухим і прогрітим.
in_schema: true       # питання піде і в розмітку FAQPage для Google
order: 10             # менше число — вище в списку
```

Порога показу тут немає: блок рендериться з будь-якою кількістю питань.
Розмітка FAQPage є тільки на головній — два FAQPage з тими самими
питаннями Google вважає дублем і може зняти сніпет з обох сторінок.

### Виправити текст на сторінці

Спершу: чи це взагалі текст із розмітки? Частина текстів — контент, і

### Викласти зміни

```bash
npm run build      # падає, якщо контент зламано
git add -A && git commit -m "опис змін"
git push
```

**Зараз `npm run build` падає завжди — і це не збій, а запобіжник.**
У проєкті лишаються чотири заглушки з шаблону (телефон, адреса, Telegram,
володілець даних у політиці), а на них продакшн-збірка спиняється
навмисно. Практичний наслідок: CI червоний на кожному push, і Cloudflare
Pages не розгортає нічого. Так і задумано — сайт із чужим телефоном
краще не публікувати. Розгортання почне працювати рівно тоді, коли
заглушки заміните справжніми даними: список — у розділі «Що замінити
перед запуском».

Якщо збірка впала не на заглушках — повідомлення так само називає файл
і пояснює, що саме виправити.

Щоб зібрати попри помилки (наприклад, подивитись локально):
`npm run build:preview`. Саме ним, поки заглушки на місці.

## Що замінити перед запуском

Домен уже підставлений (`avtoskloua.com` в `astro.config.mjs` і
`public/robots.txt`). Лишилися чотири заглушки:

| Файл | Що |
|---|---|
| `src/content/contacts.yml` | `phone_main` і `viber` — замість демонстраційного `+380671234567` |
| `src/content/contacts.yml` | `telegram` — замість демонстраційного `remont_skla`: інакше кнопка веде до чужої людини |
| `src/content/contacts.yml` | `address` — замість «вул. Хрещатик 12, Київ» |
| `src/pages/polityka-konfidentsiynosti.astro` | `OPERATOR` — назва ФОП або ТОВ і РНОКПП замість «ПРІЗВИЩЕ ІМЯ ПО БАТЬКОВІ» |

**Про це не треба памʼятати.** `npm run build` не пройде, поки в проєкті
лишається бодай одна заглушка з цього списку — валідатор назве файл і
пояснить, чим саме загрожує кожна. У прев'ю (`npm run build:preview`)
це лише попередження, тож локально розробляти з ними нормально.

Тексти й фотографії заглушками не вважаються: збірку вони не
спиняють, це звичайний контент.

Змінні оточення в Cloudflare Pages:

```
PUBLIC_GTM_ID             — Google Tag Manager (звичайна змінна)
TELEGRAM_BOT_TOKEN        — Secret
TELEGRAM_CHAT_ID          — Secret
TELEGRAM_WEBHOOK_SECRET   — Secret
```

Привʼязки: `RATE` → KV namespace (обмеження частоти заявок),
`DB` → база D1 (заявки та їхні стани).

## Telegram-бот

Заявки з форми приходять власнику повідомленням у Telegram. Потрібні
дві речі: токен бота і id чату, куди писати.

### 1. Створити бота

У Telegram знайдіть **@BotFather** → `/newbot` → назва → ім'я користувача
(має закінчуватись на `bot`). У відповідь прийде токен виду
`1234567890:AA...`.

### 2. Покласти токен локально

```bash
cp .dev.vars.example .dev.vars
```

Вставте токен у `.dev.vars`. **Цей файл у git не потрапляє** — репозиторій
публічний, а з токеном будь-хто зможе писати від імені бота і читати
заявки клієнтів. Токен нікому не пересилайте: якщо він десь засвітився,
`/revoke` у @BotFather видає новий.

### 3. Дізнатися chat_id

Напишіть своєму боту будь-що в Telegram (спершу `Start`), потім:

```bash
npm run telegram:chat-id
```

Команда покаже знайдені чати. Впишіть потрібний id у `.dev.vars`.
Свій chat_id не видно в інтерфейсі Telegram — його віддає лише API,
тому й знадобився скрипт. Токен він читає з файлу і ніколи не друкує.

**Якщо бот скаржиться на webhook.** Telegram не дозволяє `getUpdates`,
поки в бота зареєстрований webhook — два способи отримувати оновлення
виключають один одного. Це означає, що бот уже десь використовується.
Скрипт покаже адресу того webhook і не чіпатиме його сам. Найчистіший
вихід — завести **окремого бота для сайту**: те, що працює на старому,
лишиться неторканим. Якщо ж той webhook більше не потрібен:

```bash
npm run telegram:chat-id -- --drop-webhook
```

Після цього все, що отримувало оновлення за тією адресою, працювати
перестане — тому прапорець і не вмикається автоматично.

### 4. Перевірити

```bash
npm run telegram:test
```

Має прийти повідомлення. Після цього перезапустіть `wrangler pages dev` —
він підхоплює `.dev.vars` сам, і форма на сайті почне слати справжні
заявки.

### Бот проти групи

`chat_id` може вказувати і на групу — тоді заявки бачать кілька людей
(власник, адміністратор, змінний майстер). Додайте бота в групу, напишіть
там повідомлення і знову запустіть `telegram:chat-id`: з'явиться id групи,
він відʼємний. Для одного власника достатньо особистого чату.

### У продакшні

Ті самі три змінні (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`,
`TELEGRAM_WEBHOOK_SECRET`) задаються в Cloudflare Pages → Settings →
Environment variables, **усі три типу Secret**. `.dev.vars` потрібен
тільки для локального запуску.

### Стан заявки

Заявка приходить двома повідомленнями: знімки (якщо є) і картка з
кнопками. Розділені вони не примхи заради — Telegram не дозволяє
кнопки під альбомом фотографій.

Стани й переходи:

| Стан | Кнопки |
|---|---|
| 🆕 Нова | `В роботу` · `Відмова` |
| 🔧 В роботі | `Виконано` · `Відмова` |
| ✅ Виконана, ✖️ Відмова | `Повернути` |

Натискання переписує ту саму картку, а не надсилає нову: одна заявка —
одне повідомлення.

Натиснути двічі не страшно: повтор того самого натиску (людина тапнула
вдруге, Telegram повторив доставку, двоє натиснули одночасно) нічого не
переписує — бот відповідає підказкою «Заявка вже в цьому стані».

Усе, що сталося із заявкою, лежить у таблиці `leads` бази D1. Номер у
картці — це `id` рядка. Схема — у теці `migrations/`:
`0001_leads.sql` (таблиця) і `0002_notes.sql` (колонка `notes`, у якій
живуть попередження про фото — інакше перший же натиск кнопки стирав би
їх із картки).

**Перед першим розгортанням треба створити базу й застосувати обидві
міграції.** Інакше кожна заявка приходитиме з рядком
«⚠️ Заявку не збережено», і ніхто цього не помітить, поки не почне
рахувати.

```bash
npx wrangler d1 create leads
npx wrangler d1 execute leads --remote --file=migrations/0001_leads.sql
npx wrangler d1 execute leads --remote --file=migrations/0002_notes.sql
```

Імʼя бази — `leads` (`avtoskloua` — це імʼя воркера, не бази; воно стоїть
у `name` конфігу). Файли перелічені по черзі навмисно: у продакшні немає
таблиці відміток, тож застосовувати їх треба руками й у порядку номерів.
Повторний прогін `0002` впаде з `duplicate column name: notes` — це
нешкідливо й означає, що колонка вже на місці.

Далі в Cloudflare Pages → Settings → Functions → D1 bindings додати
привʼязку з іменем `DB` до створеної бази.

**Порядок має значення: спершу міграція, потім код.** Функції читають усі
колонки, які знають, — зокрема `notes`. Якщо розгорнути новий код на базу,
де міграція `0002` ще не застосована, зламаються **всі кнопки** під
картками: запит до бази впаде, і бот перестане відповідати на натискання.
Заявки при цьому продовжать приходити, тож помітно це стане не одразу.
Те саме правило чинне для кожної наступної міграції.

**Локально міграції накочуються інакше** — командою, яка сама пам'ятає,
що вже застосовано (таблиця `d1_migrations` у базі):

```bash
npx wrangler d1 migrations apply DB --local --persist-to .wrangler/state -c wrangler.local.toml
```

Вона бере всі файли з `migrations/` за порядком номерів; прогнати її
двічі безпечно — другого разу вона просто нічого не знайде. Перевірити,
що колонки на місці:

```bash
npx wrangler d1 execute DB --local --persist-to .wrangler/state -c wrangler.local.toml --command "PRAGMA table_info(leads)"
```

**Чому локальні команди різняться від продакшнових.** `wrangler pages dev`
розуміє привʼязку з прапорця (`--d1 DB`), а `wrangler d1 …` — ні, тож
локально їм завжди потрібен `-c wrangler.local.toml`. Команда
`d1 execute <імʼя> --remote` натомість звертається до бази **за іменем**
через API акаунта, і конфігу не потребує — саме тому продакшнові рядки
вище йдуть без `-c`. А от `d1 migrations apply --remote` конфіг вимагає
(«No configuration file found. Create a wrangler.jsonc file to define
your D1 database»), і той конфіг мусив би містити справжній
`database_id`, який суперечить локальному `"DB"` — тому в продакшні
міграції застосовуються файлами, а не цією командою.

У git `wrangler.local.toml` не потрапляє (він у `.gitignore`), тож у
свіжому клоні його треба створити самому. Ось увесь вміст:

```toml
# Тільки для локальних команд wrangler d1 — у git не потрапляє.
#
# Потрібен, бо `wrangler d1 execute` не вміє брати привʼязку з
# прапорця, як це робить `pages dev --d1 DB`. У продакшні привʼязка
# задається в панелі Cloudflare Pages, і цього файлу там немає.
#
# database_id навмисно "DB", а не довільний рядок: саме такий id
# `wrangler pages dev dist --d1 DB` підставляє сам, коли прапорець не
# містить `=<ref>`. Локальне сховище D1 — файл на диску, підписаний
# хешем цього id, тож без збігу `d1 execute` і `pages dev` бачили б
# дві різні порожні бази.
name = "avtoskloua"

[[d1_databases]]
binding = "DB"
database_name = "leads"
database_id = "DB"
```

`database_id` у ньому мусить бути саме `"DB"`, а не довільний рядок:
локальне сховище D1 — файл на диску, підписаний хешем цього id. Якщо
значення розійдеться з тим, що `pages dev --d1 DB` підставляє сам,
`d1 execute` і `pages dev` дивитимуться у дві різні порожні бази —
міграція ляже в одну, а сервер читатиме з іншої. Саме так один прогін
уже дав заявку з номером `0` і рядком «Заявку не збережено» при живій
таблиці.

**Вебхук реєструється один раз** після того, як сайт уже на домені:

```bash
npm run telegram:webhook -- https://avtoskloua.com/api/tg
```

Скрипт спершу покаже, що зареєстровано зараз, і не затре чужий вебхук
мовчки. Зняти: `npm run telegram:webhook -- --delete`.

## Розгортання

Cloudflare Pages, гілка `main`:

- Build command: `npm run build`
- Build output: `dist`
- Прев'ю-гілки: `npm run build:preview`

Форма працює через Pages Functions (`functions/api/lead.ts`) — окремий воркер
не потрібен, той самий домен, без CORS.

### Заголовки

`public/_headers` — CSP, HSTS, `nosniff`, безстроковий кеш для `/_astro/*`.
Файл прокоментований: там написано, чому в `script-src` є `'unsafe-inline'`
(Astro вбудовує скрипти в HTML, GTM додає теги інлайном).

## Архітектура

```
Контент (YAML) ──> validate-content.mjs ──> Astro build ──> Cloudflare Pages
```

**Ключовий принцип:** зламати продакшн неможливо. Помилка в контенті зупиняє
збірку, живий сайт лишається в останньому робочому стані.

### Валідація контенту

Два інструменти з різними ролями:

- `src/content.config.ts` і `src/lib/site.ts` — zod-схеми: типи,
  обовʼязковість полів, межі значень. Падають під час збірки.
- `scripts/validate-content.mjs` — те, чого схеми не вміють:
  заглушки з шаблону, існування фотографій галереї на диску та їхній
  розмір по короткій стороні, пороги показу блоків.

### Запобіжник для самої документації

Той самий скрипт перевіряє і README: кожен шлях, узятий тут у зворотні
лапки, мусить існувати на диску. Немає — попередження з назвою шляху.
Помилкою це не робиться навмисно: застарілий рецепт не причина не
випускати сайт.

Перевіряються лише схожі на шлях рядки — з розширенням або зі скісною
рискою. Команди (`npm run build`), значення (`+380XXXXXXXXX`), адреси
і глоби з `*` не чіпаються. Рядок «перевірено шляхів із README» у
статистиці показує, скільки їх узято до уваги.

Причина проста: рецепти вище називають конкретні файли, і рецепт,
що вказує на перенесений файл, шкодить більше, ніж його відсутність.
Чого перевірка не ловить — це посилання на **не той** наявний файл;
тут допоможе тільки уважність.

Раніше вони навмисно дублювали одне одного, бо контент редагував власник
через CMS і йому потрібні були пояснення українською. CMS більше немає,
дублювання прибрано.

Окремо валідатор ловить дві речі, які не є «контентом», але ламають запуск:
заглушки з шаблону (див. вище) і неправильні шляхи до фото галереї — коли
шлях не починається з `/src/`.

**Про шлях до фото варто знати окремо.** Він має починатися з `/src/`:
поле описане через `image()`, і шлях на кшталт `/assets/…` Astro шукає
в теці `public/`, де файлу немає. Валідатор ловить цю помилку до збірки.

### Умовні блоки

Порогові значення в `src/lib/site.ts`:

- галерея рендериться від **4 опублікованих пар**
- відгуки — від **3 штук**

Менше — блок не з'являється. Порожні рамки гірші за відсутній блок.

## Бюджет продуктивності

Перевіряється в CI (`lighthouserc.json`), збірка падає при порушенні:

| Метрика | Ліміт |
|---|---|
| Performance | ≥ 0.95 |
| Accessibility | ≥ 0.95 |
| SEO | 1.0 |
| LCP | ≤ 2000 мс |
| CLS | ≤ 0.02 |
| `uses-responsive-images` | без зауважень (жодного зображення, більшого за потрібний розмір) |

Ще два бюджети — на рівні попередження, збірку не спиняють: вага сторінки
до 500 КБ і невикористаний JS до 10 КБ.

Емуляція: середній Android, 4× уповільнення CPU, три прогони.

**Чого не робити:** не додавати зовнішні шрифти, не вбудовувати Google Maps
iframe, не ставити React заради одного компонента. Кожне з цього самотужки
з'їдає бюджет.

### Про шрифт

Заборона на зовнішні шрифти лишається в силі — вона про запит на чужий домен
перед першим рендером. Шрифт сайту (Onest, SIL OFL) інший випадок: один
варіативний woff2 на 34 КБ із вирізаною кирилицею й латиницею, на нашому ж
домені, з `preload` і кешем на рік. Файл — `public/fonts/onest-var.woff2`,
ліцензія поруч.

Ціна виміряна, а не припущена: LCP 916 → 1371 мс при ліміті 2000. Системний
шрифт був головною причиною, чому сайт читався як шаблон, і півсекунди
запасу за це — прийнятний обмін. Якщо колись знадобиться повернути LCP,
найдешевший крок — `font-display: optional` замість `swap`: перший візит
побачить системний шрифт, повторні — свій.

Ім'я файлу не містить хеша, а кешується на рік. Оновлюєте шрифт — давайте
файлу нове ім'я.

## Аналітика

Один делегований слухач у `src/components/Analytics.astro` ловить усі
конверсійні кліки. Події: `click_phone`, `click_viber`, `click_telegram`,
`form_submit`, `form_step`, `scroll_75`.

`form_step` шле скрипт форми заявки (`src/components/LeadForm.astro`) при
кожному переході між кроками майстра — несе номер кроку (`step`), на який
перейшли. Без неї неможливо дізнатися, на якому екрані майстра люди йдуть.

Атрибут `data-cta` на посиланні дає розбивку за місцем: `header`, `menu`,
`hero`, `sticky`, `contacts`. Значення `form_home`, яке форма заявки
ставить через проп `placement`, сюди не належить: слухач читає `data-cta`
лише з `a[href]` (`tel:`/`viber:`/`t.me`), а кнопка відправки форми —
не посилання, тож це значення в аналітику не потрапляє.

GTM вантажиться через 1,2 с після `load` — аналітика не впливає на LCP.
