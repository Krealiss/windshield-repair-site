# Кешбек: накопичення — план реалізації

> **Для агентних виконавців:** ОБОВʼЯЗКОВА ПІДСКІЛ: використовуйте
> superpowers:subagent-driven-development (рекомендовано) або
> superpowers:executing-plans, щоб виконувати план задача за задачею.
> Кроки позначені `- [ ]` для відстеження.

**Мета:** нараховувати клієнтові 10% від суми закритої заявки й показувати
накопичене там, де з ним говорять.

**Архітектура:** журнал нарахувань окремою таблицею; після кожної зміни
заявки одна атомарна операція дописує різницю між «належить зараз» і
«вже записано». Операція живе в `shared/`, бо її кличуть обидва
записувачі — Worker CRM і вебхук бота в Pages Functions.

**Технології:** Astro 7 + Cloudflare Pages Functions, окремий Worker на
Hono в `crm/`, спільна база D1, тестового раннера немає.

**Спека:** `docs/superpowers/specs/2026-10-21-cashback-design.md`

## Глобальні обмеження

- Видимий текст і коментарі — українською, UTF-8. Стани й ролі в базі латиницею.
- Нових залежностей не додавати. Нових класів стилів у CRM не заводити.
- `npm run build` має проходити (код 0), `npm run validate`, `npm run check:functions`, `npm run crm:check`, `npm run build:preview` — теж.
- CRM розрахована на телефон: нічого вужчого за 44 пікселі.
- Відсоток — 10, константою в коді, не змінною оточення.
- Округлення вниз, у копійках.
- Сторно — окремим рядком; жоден рядок журналу не редагується й не видаляється.
- Рядок кешбеку в картці Telegram — лише коли баланс більший за нуль.
- Міграція не несе бекфілу: у базі немає жодної закритої заявки.
- Жодного списання, строку дії, передачі чи повідомлення клієнтові.

## На що дивитись рецензентові

1. **Сума нуль.** Гарантійний ремонт закривають на 0 ₴. Належить 0, різниця 0, рядка в журналі немає — і це не «не нарахували». Тест у Задачі 1.
2. **Повторна доставка того самого натискання.** Telegram повторює доставку; друга синхронізація мусить не дописати нічого. Тест у Задачі 1.
3. **Гонка двох записувачів.** CRM і бот міняють заявку майже одночасно. Різниця рахується всередині одного `INSERT … SELECT`, тож другий запит бачить рядок першого й дописує нуль. Тест у Задачі 1.
4. **Номер із ручної заявки.** Кешбек ключується номером. Якщо `/new` збереже номер в іншому вигляді, ніж форма сайту, баланс розʼїдеться на два. Тест у Задачі 2.
5. **Повернення в роботу зі старою сумою.** «Повернути» не чистить `amount`; після повторного закриття кнопкою бота належить стільки ж, скільки було. Тест у Задачі 2.

### Задача 1: Таблиця й правило синхронізації

**Файли:**
- Створити: `migrations/0008_cashback.sql`
- Створити: `shared/cashback.ts`
- Перевірка: тимчасовий скрипт у скретчпаді, база в скретчпаді

**Інтерфейси:**
- Споживає: `LeadRow` із `shared/card.ts` (поля `id`, `phone`, `status`, `amount`)
- Віддає:
  - `export const CASHBACK_PCT = 10`
  - `export function earnedKop(lead: { status: string; amount: number | null }): number`
  - `export async function syncCashback(db: D1Database, lead: { id: number; phone: string; status: string; amount: number | null }): Promise<void>`
  - `export async function balanceKop(db: D1Database, phone: string): Promise<number>`
  - `export type CashbackRow = { id: number; lead_id: number; kop: number; created_at: string }`
  - `export async function ledgerByPhone(db: D1Database, phone: string): Promise<CashbackRow[]>`

- [ ] **Крок 1: Міграція**

`migrations/0008_cashback.sql`: таблиця `cashback` з колонками `id`
(INTEGER PRIMARY KEY AUTOINCREMENT), `phone` (TEXT NOT NULL), `lead_id`
(INTEGER NOT NULL), `kop` (INTEGER NOT NULL, відʼємне — сторно),
`created_at` (TEXT NOT NULL); індекси за `phone` і за `lead_id`.
Коментар угорі — навіщо журнал, а не колонка з балансом.

- [ ] **Крок 2: Написати перевірку, яка падає**

Скрипт у скретчпаді, база в скретчпаді (`--persist-to` у власну теку,
не в `.wrangler/state` проєкту). Прогнати послідовність на одній заявці
й звіряти баланс після кожного кроку:

| Дія | `earnedKop` | Рядків у журналі | Баланс |
|---|---|---|---|
| заявка `new`, суми немає | 0 | 0 | 0 |
| закрили на 120000 коп | 12000 | 1 | 12000 |
| та сама синхронізація вдруге | 12000 | 1 | 12000 |
| суму виправили на 90000 | 9000 | 2 | 9000 |
| повернули в роботу | 0 | 3 | 0 |
| закрили знову на 90000 | 9000 | 4 | 9000 |
| закрили на 0 (гарантія) | 0 | 5 | 0 |

Окремо: два `syncCashback` поспіль без `await` між ними (`Promise.all`)
після закриття на 120000 дають баланс 12000, а не 24000.

- [ ] **Крок 3: Запустити й переконатися, що падає**

Очікується: помилка «no such table: cashback» або відсутній модуль.

- [ ] **Крок 4: `earnedKop`**

Повертає `Math.floor(amount * CASHBACK_PCT / 100)`, коли
`status === 'done'` і `amount !== null`; інакше 0.

- [ ] **Крок 5: `syncCashback` одним запитом**

Різниця рахується **всередині SQL**, інакше два одночасні виклики
допишуть по повному нарахуванню кожен. Запит рівно такий:

```sql
INSERT INTO cashback (phone, lead_id, kop, created_at)
SELECT ?, ?, ? - s.total, ?
  FROM (SELECT COALESCE(SUM(kop), 0) AS total FROM cashback WHERE lead_id = ?) AS s
 WHERE ? - s.total <> 0
```

Порядок значень: `phone`, `lead_id`, належить, мітка часу, `lead_id`,
належить.

- [ ] **Крок 6: `balanceKop` і `ledgerByPhone`**

Перший — `SELECT COALESCE(SUM(kop), 0)` за номером. Другий — рядки за
номером, найновіші зверху.

- [ ] **Крок 7: Запустити перевірку**

Очікується: усі рядки таблиці з Кроку 2 збігаються, гонка дає 12000.

- [ ] **Крок 8: Коміт**

```bash
git add migrations/0008_cashback.sql shared/cashback.ts
git commit -m "Журнал кешбеку й правило синхронізації"
```

### Задача 2: Нарахування відбувається саме

**Файли:**
- Змінити: `crm/src/db.ts` (кінець `applyChange`)
- Змінити: `functions/api/tg.ts` (після успішного `UPDATE`)
- Перевірка: стенд CRM зі сміттєвим токеном, база в скретчпаді

**Інтерфейси:**
- Споживає: `syncCashback`, `balanceKop` із Задачі 1

- [ ] **Крок 1: Підключити в CRM**

`applyChange` закінчується `return getLead(db, id)`. Перед поверненням
викликати `syncCashback` для прочитаного рядка. Це покриває всі
маршрути CRM, що міняють стан або суму: `/close`, `/decline`, `/undo`.

`assignLead` не чіпати: призначення веде лише `new → in_work`, а там не
належить нічого. Написати це коментарем, щоб наступний не вважав
пропуском.

- [ ] **Крок 2: Підключити в боті**

У `functions/api/tg.ts` після перевірки `written.meta.changes !== 0`
викликати `syncCashback` із рядком, у якому стан замінено на `target`
(сума в рядку вже прочитана). Бот суму не міняє ніколи, але міняє стан
— отже «Виконано» і «Повернути» мусять рухати журнал.

- [ ] **Крок 3: Перевірка наскрізь на стенді**

Підняти CRM на власній базі зі сміттєвим токеном. Завести заявку через
`/new` і пройти:

| Дія | Баланс за номером |
|---|---|
| створили заявку | 0 |
| закрили через `/close` на 1200 | 12000 коп |
| `/close` ще раз на 900 | 9000 коп |
| `/undo` | 0 |
| `/close` на 900 | 9000 коп |

Окремо перевірити номер із Задачі «Review Focus» 4: номер, збережений
через `/new`, і номер, збережений формою сайту, мають бути однаковими
рядками — порівняти `SELECT DISTINCT phone FROM leads`.

## Поза цим планом

Списання, строк дії, передача балансу, повідомлення клієнтові,
різні відсотки за послугу, звіт «скільки роздано». Кожне з них
спирається на відповіді власника майстерні, перелічені в спеці.

Розгортання на бойову базу: міграція `0008` накочується **до** коду, як
і кожна попередня.
